# Ploop 实施与验收路线

日期：2026-11-03。M0 已完成真实 Codex PoC；M1 的单机 SQLite Hub / Bridge、持久 outbox、去重与保守恢复已实现，M3 的基础工作台和文本 Web SDK 已实现。浏览器真实修复、Hub 重启后取消、原生取消与超时见[实测记录](verification/mvp-2026-11-03.md)。下列通过条件仍是完整阶段目标，不能据局部通过宣布整阶段完成；公网、安装分发、自动发布及完整故障矩阵尚待实施或验证。

## M0 验证安装和原生 Agent 接口

先做一个最小 CLI 探针和可复现示例仓库，暂不开发完整控制台。锁定 Node、包管理器、Codex 版本和 SQLite 驱动；生成该 Codex 版本的协议类型，确认 stdio 握手、真实 turn、输入补充、审批、取消和会话恢复。

建议首批覆盖 macOS arm64 与 Linux x64，逐个平台实测后再列为支持平台。Windows 在进程树监督、文件权限和 Git 路径经过验证前列为待支持。

通过条件：

- 干净环境能够按公开说明安装、启动、诊断与卸载；不依赖作者电脑上的应用内绝对路径。
- 示例仓库的原始验收先稳定失败，真实 Agent 修改后同一验收通过；保存 base/head SHA、命令和结果。
- 取消后有终态确认，遗留进程与文件能被解释；恢复 ID 无效时能从 Ploop 上下文开始新会话。
- 标明实际使用的认证方式；列举模型不算成功推理，官方接口文档也不算运行验证。
- SQLite 驱动完成目标平台安装、事务、备份恢复和突然退出测试；版本与上游已知问题范围记录在案。

这一步需要真实 Agent 调用，可能消耗对应账户或 API 用量。2026-11-03 已通过官方本地 CLI 完成一次调用；Ploop 没有读取或改写用户登录文件。协议异常和部分取消回归使用可控执行器；新增真实原生取消、超时及 Hub 重启后取消检查。会话恢复、干净安装和完整平台矩阵仍未完成。

## M1 建立任务和证据的可靠传递

当前已提供本地单实例版本：显式仓库绑定、审批、持久 claim / journal / outbox、租约过期不自动重派、未知执行保留。已验证重复领取、丢失结果回执、Hub 重启和 Bridge journal 重开；磁盘满、硬退出的完整矩阵、清理重试和发布阶段尚无完整覆盖。

实现单实例 Hub、SQLite 迁移、设备配对、显式仓库绑定、任务领取、持久事件、Bridge journal/outbox，以及取消和清理所有权。以同一个生产编排路径接入可控执行器验证故障；可控执行器的通过结果只证明编排，不证明真实 Agent 能力。

必须覆盖的故障及预期：

| 情况 | 必须观察到的结果 |
|---|---|
| 同一任务重复下发，回执丢失 | 只启动一个有效 attempt，重发可安全回执 |
| Agent 已结束，结果回传断网 | 本地结果保留，重连后补报，不重新执行修复 |
| Hub 或 Bridge 突然退出 | 重启后能核对已领取任务、原进程和工作区，不悄悄丢任务 |
| 租约过期后旧 Bridge 回来 | 旧代次消息可识别；未知在途执行先核对，不立即双跑 |
| 准备、等待审批、执行、验证时取消 | 不启动后续阶段；确认停止后保留已有成果 |
| push、创建 PR 或最终上报期间取消 | 核对外部真实结果，避免取消后隐式继续发布 |
| 清理失败、dirty 或未推送提交 | 保留所有权和目录，能够重试和解释保留原因 |
| 附件过大、格式错误、磁盘满 | 返回明确失败原因，保留已完成事实，不留下伪完整证据 |
| 协议版本、能力或 JSON 不匹配 | 明确拒绝或降级，不用默认值假装支持 |
| Agent / 测试尝试使用 Git helper、SSH agent 或其他发布凭证 | 无法绕过受控发布阶段；隔离无法落实时降级为手动发布 |
| Agent 改测试入口、删验收，或验证后源文件继续变化 | 维护者验收保持原语义；受影响的验证记录失效 |

通过条件是每项都能从持久事件、数据库和本地状态还原原因。先通过单任务测试再放开多设备；不以一个正常路径演示替代这些回归。

## M2 完成 GitHub 修复闭环

接入真实 Codex adapter 和 GitHub。Agent 修改工作区；独立验证器运行项目验收；Bridge 推送任务分支；Hub 创建或核对 draft PR。PR 归属、远端分支和 commit 使用结构化身份关联。

验证针对冻结候选 commit 的独立快照执行；验收入口和配置来自维护者认可的版本，源文件不随 Agent 后台进程继续变化。记录验收材料摘要，推送完全相同的已验证 SHA；PR head 更新后旧结果不能继续显示为当前通过。

通过条件：

- 真实反馈证据被写入明确版本的任务上下文，能追到原始附件和日志。
- 没有独立验证结果的 PR 清楚显示未验证；Agent 自述不直接变成 checks 通过。
- 创建 PR 后响应丢失时能够查回同一个 PR；不通过重复运行 Agent 解决外部调用结果不明。
- webhook 验签、delivery ID 去重与异步处理通过生产边界测试；同一 delivery 重投不重复处理。
- 人工 merge 后工单可显示已合并，部署保持待确认；人工确认上线后再更新面向用户的状态。

GitHub 的自动化发布逻辑仍未实现。本次开发会将 PoC 代码和验证记录提交到用户指定的 Ploop 仓库作为 draft PR，与产品内自动发布能力分开记录。

## M3 完成 SDK 和开发者安装体验

当前已有无框架文本 SDK、订单浏览器示例、收件箱 / 详情 / 项目 / Bridge 页面及有限只读回执。源码启动步骤见[本地 MVP 指南](本地MVP.md)。React 组件、截图附件、公网接入、正式设备配对、升级恢复和安装包仍未实现。

提供无框架依赖的 Web SDK、一个 React 示例、可上传截图的反馈入口，以及收件列表、工单详情、执行时间线、项目/设备设置四个基础页面。

通过条件：

- 从用户浏览器提交反馈到生成 draft PR 的完整流程可复现，并区分用户、管理员、Bridge 的权限。
- 开发环境 localhost 接入和生产 HTTPS Hub 接入都有实际示例，跨域、认证、附件上传和设备休眠表现可解释。
- 公开采集 key 无法读取反馈或启动任务；输入的文本、附件和 URL 不被当作任意命令或自动抓取授权。
- 用户只读回执只能查看本工单的有限状态，不能访问日志、附件、其他工单或管理动作。
- 默认采集范围、附件与日志预算、数据保留及删除可配置；截断会在界面和上下文中保留标记。
- 升级前可备份，升级失败可恢复，卸载不默认销毁工作区和反馈数据。

## M4 小范围外部试用后发布

邀请少量真实开发者尝试安装与修复，记录问题而不预设满意度。用约 10 个可复现问题构建初始检查集，这是发现失败模式的起点，不是统计上充分的产品效果证明。

| 维度 | 采集方式 |
|---|---|
| 安装 | 首次成功所需步骤、卡点、运行时和平台 |
| 正确性 | 独立验收结果与人工对修复意图的审查 |
| 效率 | 完整任务的 tokens、耗时、人工轮次、CPU 和进程族峰值内存 |
| 可靠性 | 重试、重复投递、断网与恢复后的外部动作和最终状态 |
| 可审查性 | PR 是否包含足够复现、修改与验证证据 |
| 采用意愿 | 是否愿意继续使用，为什么放弃或限制授权 |

对照基线使用相同问题、仓库版本、模型和权限，分别记录冷启动与复用会话。工具不提供的数据记为未知；不能把 API 标价当订阅实际成本，也不能把总日志字节数当模型 tokens。

发布前完成维护者拥有的 package scope、许可证及依赖清单、稳定安装包、已验证的平台矩阵、升级/备份/卸载说明、限制说明和贡献指南。只有实际通过的能力进入 README 功能列表。

## 后续扩展顺序

先根据试用失败原因决定扩展。可能的顺序是：第二种 Agent → 外部工单/MCP → 可选回放和本地预览 → GitHub Actions / 容器 worker → 团队权限与其他 Git 平台。公网预览、多租户计费和自动部署需要各自的验证，不随“支持更多 Agent”一起默认开放。
