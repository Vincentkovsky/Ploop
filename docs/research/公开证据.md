## 2 对架构有用的源码观察

| 观察 | 包内位置 | 对 Ploop 的设计推导 |
|---|---|---|
| 设备主动接入实时通道，回传走 REST；接口有配对、心跳、ack、events、result | `src/daemon.mjs:2`；`src/api.mjs:87` | 本地 Bridge 路线可行；Ploop 可以自定更小的出站协议 |
| API / App 基址可配置 | `src/config.mjs:20` | 可研究替换控制服务，但改地址本身不等于服务端兼容 |
| 开始执行前登记运行项，重复任务仍回执；持久 handled 列表有容量限制 | `src/daemon.mjs:2188`、`:69`、`:612` | 去重、接收回执、执行完成应分别建模 |
| 结果请求有限重试；最终失败后仍清 inflight 并记 handled | `src/api.mjs:72`；`src/daemon.mjs:2462` | 不能从这份实现推导 exactly-once 或永不丢结果；Ploop 需要持久 outbox |
| 输入显式包含 task、feedback、answers、attachments、MCP 和自定义指令 | `src/executor.mjs:77` | 上下文是明确交付的数据，并非任意聊天记忆自动继承 |
| 无法恢复原会话时重建任务、计划、摘要和近期对话 | `src/rehydration.mjs:54`、`:119` | Ploop 应独立持有可重建的 TaskContext |
| 三种 Agent 分别配置创建/恢复会话、环境与模式 | `runner/lib/acp/harnesses.mjs:303` | 统一接口应保留不同 Agent 的能力和失败原因 |
| build 适配采用宽松权限，子进程继承环境，工作区逻辑可能复制 `.env*` | `runner/lib/acp/harnesses.mjs:447`、`:561`、`:583`；`src/executor.mjs:172`；`src/workspace.mjs:356` | worktree 不等于安全沙箱；Ploop 自定执行与环境策略 |
| 取消先走协议，再升级 TERM/KILL；停止时某些路径会推送 WIP | `src/executor.mjs:383`；`src/daemon.mjs:2405` | 取消的含义必须覆盖副作用，不能直接照搬停止行为 |
| Bridge 推分支，服务端负责 PR；预览运行真实项目命令 | `src/daemon.mjs:2380`、`:2422`；`src/preview.mjs:14` | Git、PR、测试与部署是不同阶段；预览仍执行仓库代码 |

这些观察建立了可研究的实现路径。云端调度、完整用户权限、数据库结构、客服调查和实际运行效果仍然未知。客户端注释关于云端共享 runner 的说明也不能证明云端当前运行的是相同版本。

## 3 哪些内容可以作为实现参考

Bridge 的 `package.json` 声明 MIT。包内没有发现独立 LICENSE、COPYING 或 NOTICE；元数据所指 GitHub 仓库在本次公开访问返回 404。另有随包 runner 的来源声明。因此本方案不把“元数据声明 MIT”扩展为对所有来源和第三方内容的授权结论。

Gleap 的 Web SDK 有公开源码和 MIT 许可证入口，可研究其采集方式；这不使 Gleap 服务端自动变成开源。[Web SDK](https://github.com/GleapSDK/JavaScript-SDK)

`self-heal-sdk` 是另一条轻量路线的公开参考：它把修复/改进请求交给 Cursor Background Agent，并提供记忆接口处理重复请求。它有 MIT 许可证入口，但本次没有做其生产行为或完整生命周期审计。[项目源码](https://github.com/andrelandgraf/self-heal-sdk)

Ploop 的默认路线是独立实现自有协议、任务、权限和界面。研究材料不进入运行时依赖；暂不复制厂商 runner、提示词和界面资产。未来实际复用组件时，逐个核对具体版本与许可来源。

## 5 对可靠性与评估的依据

GitHub 文档说明 webhook 签名校验、快速响应、异步处理以及 delivery ID 的用途；重投可能使用相同 delivery ID。Ploop 需在持久化边界完成去重与核对。[签名校验](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)、[最佳实践](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)

SQLite 文档说明 WAL 的本机文件系统要求与单写事务约束。采用 SQLite 是简化安装的设计取舍，不是已经做过吞吐和资源测量。[WAL](https://sqlite.org/wal.html)、[事务](https://sqlite.org/lang_transaction.html)

Langfuse 的 trace / session 分组与数据集评估可参考；Ploop 的执行事实仍由自身事件和证据记录持有，外部观测作为可选出口。[Trace 最佳实践](https://langfuse.com/docs/observability/best-practices)、[评估概述](https://langfuse.com/docs/evaluation/overview)

当前没有 Ploop 的成功率、tokens、延迟、CPU 或内存测量。接下来必须用真实 Agent、真实测试仓库及故障注入验证，而不是用公开产品介绍替代。
